Anthropic の skill-creator(元の手順書は `references/upstream-SKILL.md`。Apache 2.0、`references/LICENSE.txt`)を、このハーネス(OpenCode・GPT-5.4 mini・会社の Windows)に合わせて短くした手順。元にある、子での並行の試験、`claude -p` での説明文の最適化、結果のビューアーは使わない(この環境では動かない・重い)。

## 前提

- 実行: `<スキルのフォルダ>\run.bat`(Mac・Linux は `run.sh`。引数は同じ)。スキルのフォルダは、読み込んだときに示される。作業フォルダから、フルパスで実行する。
- スキルは、フォルダ 1 つ。`SKILL.md`(必須。先頭の frontmatter に `name` と `description`)と、必要なら `scripts/`(決まった処理。Python の標準ライブラリで)、`tests/`、`references/`(長い資料)、`run.bat`・`run.sh`(スクリプトの入口)。
- **読まれ方:** `name` と `description` は、毎回すべての会話で読まれる。本文は、モデルが使うと決めたときだけ。`references/` は、本文が指したときだけ。だから、説明文は短く、本文は要点だけ、細部は `references/` に分ける。
- 置き場所: このハーネスのリポジトリ(`skills/`・`agents/`・`AGENTS.md` がある)なら `skills/<名前>/`。ほかのフォルダでは `.opencode/skills/<名前>/`(そのフォルダの中だけで使える)。`init` が自動で選ぶ。AI_work の自動化は、`automation-builder` の `new` で作る。

## 守ること

- 頼まれたスキルだけを作る・直す。既存のスキルの名前(フォルダ名と `name`)は変えない。
- スキルに、キー・パスワード・個人情報・接続先の値を書かない(設定は `config.local.json` に分け、見本は `config.sample.json`)。
- 説明と違う動きをするもの(隠れた送信・削除など)は作らない。`pip` 以外の導入が要るものは作らない(共通ルール)。

## 作る

1. **何をするスキルかを決める。** 会話にやり方が出ていれば(「これをスキルにして」)、先にそこから拾う: 使った道具、順序、ユーザーが直したこと、入力と出力の形。決めることは次の 4 つ。分からないものだけを、まとめて 1 回聞く。
   - 何ができるようになるか / いつ使うか(ユーザーが言いそうな言葉)/ 出力の形 / 決まった処理(スクリプトにする)はあるか
   - 一覧に似たスキルがあれば、新しく作らず、そのスキルを直すことを提案する。
2. **雛形を置く。** 名前は英小文字・数字・ハイフン(例: `cost-report`)。同名があれば止まる(上書きしない)。

   ```
   run.bat init cost-report
   run.bat init cost-report --script
   ```

   `--script` は、`run.bat`・`run.sh`・`scripts/`・`tests/` も置く(計算・変換・集計など、毎回同じ処理があるとき)。
3. **`description` を書く。** 「何をするか」と「いつ使うか(言いそうな言葉を 2〜3 個)」を、80 文字くらいまで(説明文の合計に上限がある)。いつ使うかは、本文ではなくここに書く(本文は、使うと決めた後にしか読まれない)。
4. **本文を書く**(下の「書き方」)。300 行まで。長い資料は `references/` に分け、本文に「〜のときだけ `references/〜.md` を読む」と書く。
5. `--script` のときは、`scripts/` の処理と `tests/` を、スキル `python-coding` に従って書き、テストを通す(`python -m unittest discover -s <スキルのフォルダ>/tests`)。
6. **点検する。** エラーが 0 件になるまで直す。ハーネスのリポジトリでは、`python run_tests.py` も通す(説明文の合計の上限なども見る)。

   ```
   run.bat check .opencode/skills/cost-report
   ```

7. **試す**(下の「試す」)。
8. 報告する: 作ったフォルダとファイル、`description`、試した結果(試せなかったことは「未確認」)。ハーネスのリポジトリでは、README のスキルの表と CHANGELOG にも書く。

## 書き方(GPT-5.4 mini に向けて)

- 節は「前提」「守ること」「手順(番号つき)」「うまくいかないとき」。命令の形で、1 文に 1 つ。
- **理由を短く添える**(「〜する(〜すると、〜になるため)」)。「必ず」を並べるより、理由がある方が守られ、書いていない場面にも広がる。本当に外せないことだけ太字にする。
- **コマンドは、そのまま使える例で書く**(引数も)。書いていないと、推測で書いて失敗する。
- **失敗したときにすることを書く**(「〜と出たら、止めて報告する」)。書かないと、別の道具を探し回り、関係の無い場所に触る。
- **頼まれたときだけする操作は、引き金の言葉を書く**(「保存して」と言われたときだけ。「これで進めよう」は依頼ではない)。
- 出力の形は、雛形で示す(見出しの並び、表の列)。例は 1〜2 個にし、例を写さないよう、一般の形も書く。
- 日付・計算・件数のように間違えやすいものは、スクリプトに出させる。
- 共通の `AGENTS.md` やほかのスキルにあることは、書かずに名前で指す(同じことを 2 か所に書くと、片方だけ直って食い違う)。
- 書いたら、初めて読む人の目で読み直し、効いていない行を消す。

## 試す

1. ユーザーが実際に言いそうな依頼を 2〜3 個作る(ファイル名・人・数値の入った、具体的なもの)。期待する結果と一緒に、`<スキルのフォルダ>/evals/cases.md` に書く。
2. 1 つずつ、`skill` でスキルを読み込み、手順のとおりに自分で実行する。出力は `.handoff/skill_<名前>/` に置く(本番のデータには書かない。試しのフォルダやコピーで)。
3. ユーザーに、依頼・結果・気になった点を見せ、意見をもらう。「問題なし」なら終わり。
4. **使われるかを確かめる。** 使うべき依頼 3 つと、似ているが使うべきでない依頼 3 つ(ほかのスキルの出番のもの)を作る。一覧のほかの説明文と並べて、正しく選ばれるかを見る。紛らわしければ、`description` の言葉を直す。
5. 直して、1〜3 をもう一度。意見が無くなるか、良くならなくなったら終わり。

直すときの考え方:

- 試した例だけに合わせない(何度も、違う依頼で使われる。一般の言い方にする)。
- 効いていない行と、無駄な作業を生んだ行を消す。
- 毎回同じ手作業(同じ計算、同じ下書きのスクリプト)をしていたら、`scripts/` に入れる。

## 直す

1. 対象の `SKILL.md` と、フォルダの中の一覧を読む(`scripts/` のソースは、それを直すときだけ読む)。
2. 名前は変えない。Git の外のスキルなら、先に `.handoff/backup/` へ写す。
3. 最小の変更を入れ、`check` と「試す」を行う。報告に、変えた行の前後を書く。

## うまくいかないとき

- `check` の「エラー:」は、その文のとおりに直す。「注意:」は、理由があれば残してよい(報告に書く)。
- `init` が「すでにあります」で止まったら、別の名前にするか、「直す」の手順にする(上書きしない)。
