name: interview
description: 計画・設計・依頼を質問で詰める手順(grill-me)。前提の決まった質問を、おすすめの答えつきで聞き、決まるまで作業しない
---

## 考え方

- 作る前に、ユーザーが本当に欲しいものと、その理由を知る。理由が分かれば、ユーザーが口にしない細かい判断も、ユーザーと同じように下せる。
- 話題を**決定の木**として扱う。1 つの決定から、その次の決定が枝分かれする。
- **事実は自分で調べ、決定はユーザーに聞く。** ファイル・ノート・資料で分かることを、ユーザーに聞かない(`file-finder` で探して自分で読む。多ければ `researcher`)。決定を、自分で答えない。
- 1 回に聞くのは、**前提がすでに決まった質問だけ**(他の質問の答えで変わる質問は、次の回へ)。
- 未決が 0 件になり、**ユーザーが「共通の理解になった」と確かめるまで、作業(実装・資料の作成)を始めない。**

実行: 作業フォルダのまま `<スキルのフォルダ>\run.bat 引数`(Mac・Linux は `run.sh`)。`cd` しない。

## 手順

1. **聞く前に調べる。** ユーザーが示したファイル・ノート・前の会話と、それにつながる資料を読む。いまどうなっているか、何が変わるかを説明できるまで読む。すでに答えのあることを聞かない。決まっていることを蒸し返さない。
2. 記録を作る(`.handoff/interview_<話題>.md`。この記録が正本。会話が長くなったら読み直す)。

   ```
   run.bat init 締付の手順書
   ```

3. **最初の発言。**
   - 依頼が具体的なとき: 依頼を自分の言葉で言い返す(200 字ほど。何を、誰のために、なぜ)。調べて分かったこと(いまの状態、影響する所、ユーザーが気づいていないかもしれない制約や近道)を添える。そのうえで、理由がまだ分からなければ、**「なぜ」を 1 つ、選択肢を付けずに**聞く。
   - 依頼が曖昧なとき: いちばん大きな未決について、**選択肢を付けない質問を 1 つ**。その答えで何が変わるかを添える。
4. **回を重ねる。** 理由が分かったら、前提の決まった質問をまとめて 1 回で聞く(多くても 5 問)。形:

   ```
   ❓ Q1 - <質問の題>: <質問の本文。選択肢があれば並べ、それぞれの得失を 1 行で>
   ➡️ おすすめ: <自分のおすすめと、その理由>

   ❓ Q2 - …
   ➡️ おすすめ: …
   ```

   - **「はい」で、おすすめを受け入れられる**書き方にする。ユーザーは「1 はい、2 は B、3 は…」と番号で答えられる。
   - 1 問ずつがよいと言われたら、1 問ずつにする。
   - 選択肢だけで答えられる質問は、`question` ツール(選択式)を使ってもよい。おすすめを最初の選択肢にする。
5. **各回の後に、記録を更新する。**
   - 決まったこと: `- D3: <内容>(決めた人: ユーザー、第 2 回)`。おすすめを受け入れられたものも「決めた人: ユーザー」。
   - 調べた事実: `- F2: <事実>(出典: パス・ページ)`。
   - 仮定: 確かめていないことは仮定に置き、後の回で確かめる(了承されたら「(ユーザーが了承)」)。
   - 未決: 次に聞くことと、その前提(`- Q5: …(前提: D3)`)。
6. **分かった部分から、言い返す。** 1 つの部分(目的と相手、ある機能の動き)が分かったら、200〜300 字でまとめて返し、「違う所・足りない所」を聞いてから次へ進む。ユーザーが言ったことはユーザーのものとして、自分が補ったことは提案として(理由つきで)書く。
7. **作り方は、何を作るかが分かってから。** 何が欲しいかが分かったら、作り方の案を 2〜3 個(得失つき)と、おすすめを、それだけで 1 つの発言にして示し、選んでもらう。ユーザーが作り方を任せてきたら、自分で決めて 1 行で伝える(記録には「AI の提案」として書き、了承を得る)。
8. **終わり方。** 未決が 0 件になったら、`check` を通す。

   ```
   run.bat check .handoff/interview_締付の手順書.md
   ```

   「まだ終わらない」の項目を片づける。残るのが「最後の確認」だけになったら、全体のまとめ(目的、成功の条件、やらないこと、決まったこと、了承された仮定)を示し、**「これで共通の理解になりましたか」**と聞く。ユーザーが確かめたら、記録の最後の確認を `[x]` にする。
9. その後の作業(資料なら `doc-writing`、計算なら `calc-check`、ノートなら `vault-notes`)は、**ユーザーが始めてよいと言ってから**。記録の決まったことに従う。

## 聞くべき範囲(台本ではない。この順に読み上げない)

- 何を作るのか、何が特別か / なぜいまか、成功とは何か
- やること・やらないこと・**失敗とみなす条件**(動いても失敗になるもの)
- いまの状態、すでに試したこと / 参考にしたいもの、避けたいもの
- 使う人・読む人、使う場面 / 期限、承認する人、社内の決まり
- 境目の場合、例外、失敗したとき / どう確かめるか(検証の方法)

## 質問の質

- **その答えで、作るものが変わる質問だけを聞く。** 変わらないことは、自分で決めて提案として書く。
- 話題に即して、具体的に聞く。ユーザーの直前の答えや、調べて分かったことに積み上げる(「2 人が今月入ったが、途中から入った人も投票できますか」)。何を知りたいか、答えで何が変わるかを添える。
- 当たり前の質問をしない。境目の場合、例外、矛盾を突く。
- ユーザーの言葉に合わせ、専門用語・手順の名前(「決定の木」「回」など)をユーザーに言わない。
- 「任せる」「どう思う」と言われたら、具体的な案を出す。
- 「もういい」「まとめて」と言われたら、そこで止め、未決と仮定を残したまま、まとめを示す。

## 守ること

- **自分の質問に、自分で答えない。** 決定を「決めた人: AI」で記録しない(`check` が問題にする)。
- 質問への答えが得られない(取り消された、返事が無い)ときは、勝手に仮定して先へ進まない。そこで止め、未決として残す。
- 実装・資料の作成・ファイルの変更は、最後の確認の後、ユーザーが始めてよいと言うまでしない(`.handoff/` の記録は書いてよい)。
