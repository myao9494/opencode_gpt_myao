# 文書の変換(Word / Excel / PowerPoint / PDF → Markdown)

スキル `doc-convert` の設計と、会社での確認。使い方そのものは [skills/doc-convert/SKILL.md](../skills/doc-convert/SKILL.md)。

## 1. なぜ要るか

- `.docx` `.xlsx` `.pptx` `.pdf` は、`read` で開いても、文章として読めない(zip や独自の形式)。社内の文書が Office と PDF 中心なら、LLM はそれらを読めないことになる。
- 読む作業は文章量が多い。変換して読む作業ごと `researcher`(子セッション)に任せれば、読んだ量はメインに入らない。

## 2. 構成

```
researcher ──(スキル doc-convert を読み込む)──▶ run.bat convert <ファイル>
                                                    │
                          scripts/convert_cli.py ─ 入力の検査(作業フォルダか roots の中か)
                                                    │
                          scripts/convert_core.py ─ 形式ごとの変換(標準ライブラリ。PDF だけ pypdf)
                                                    ▼
                          .handoff/converted/<元の名前>.md   ← 保存
                                                    │
                          画面に出るのは「保存先・規模・目次(行番号つき)・注意」だけ
                                                    ▼
                          researcher が、目次の行番号を使って、必要な部分だけを read する
```

- 本文を画面に出さないのは、変換した直後に全文がコンテキストに入ると、変換の意味が薄れるため。目次の行番号で、必要な部分だけを読ませる。
- 使えるのは `researcher` だけ(`agents/researcher.md` の `skill` と `shell` の許可)。メインから使うときは、`researcher` に任せるか、`/convert-doc` を使う。

## 3. 方式

| 形式 | 方式 | 変換するもの |
|---|---|---|
| `.docx` | 標準ライブラリ(zip と XML) | 見出し(スタイル名とアウトラインレベル)、段落、箇条書き・番号つき(階層)、表(結合セルは空欄で補う)、外部リンク、変更履歴(承認後の文章) |
| `.xlsx` | 標準ライブラリ | 表示中のシートを、Markdown の表に。文字列、数値、真偽値、日付(書式から判定して日付にする。1900 年・1904 年方式)、保存済みの数式の結果 |
| `.pptx` | 標準ライブラリ | スライド順に、題名、本文(箇条書きの階層)、表、グループ内の図形の文字、ノート。非表示のスライドは印をつける |
| `.pdf` | `pypdf`(`requirements.lock` に固定) | ページごとの文字 |
| `.csv` `.tsv` | 標準ライブラリ | 表。文字コードは UTF-8(BOM つき含む)→ Shift_JIS(cp932)の順に試す |

- `pypdf` は、PDF にだけ要る。無くても、そのほかの形式は変換できる(`run.bat check` で分かる)。
- Office の形式を標準ライブラリで読むのは、PyPI に直接つなぐ間は、依存を増やしたくないため。MarkItDown のような変換ツールは採用しなかった(依存が多くなる見込みで、会社での取得と固定の手間が増える。実際の依存の数は確認していない)。
- 古い形式(`.doc` `.xls` `.ppt` `.rtf`)は未対応。Office で新しい形式に保存し直してもらう。Office の COM で変換する案もあるが、会社で試すまで入れない。

## 4. 変換されないもの

画像・図・グラフ・SmartArt・テキストボックスの中の文章、Word のヘッダー・フッター・脚注・コメント、Excel のピボットテーブルの定義(表示されている値は入る)、計算結果が保存されていない数式(空欄)、スキャンした画像の PDF(OCR は未対応)。

これらは、変換のたびに「注意:」として画面に出る。`doc-convert` のスキルは、返答の「未確認」に必ず反映するよう指示している。

## 5. 安全の設計

| 心配 | 対策 |
|---|---|
| 変換した文章の中の指示 | 文章は、データとして出すだけ。スキルが「従わない・報告する」と指示する。コードは内容を解釈しない |
| 作業フォルダの外の、見せたくないファイルを読む | `read` の権限を経由しないため、スクリプトの中で強制する。読めるのは、作業フォルダと、設定(`config.local.json`、無ければ `file-finder` の `roots`)の中だけ。`..` やシンボリックリンクで外へ出られない(実体のパスで判定) |
| 書き込み | `.handoff/converted/` だけ。出力先は指定できない。同名は上書きせず、`_2`、`_3` を付ける。元のファイルは変更しない(テストで確認) |
| zip 爆弾 | ファイル数、全体の展開後の大きさ、部品 1 つを読む量に上限。入力は 200 MB まで |
| XML の外部実体・膨張(DTD) | `<!DOCTYPE` と `<!ENTITY` を含む XML は処理しない |
| 実行 | `eval`、`exec`、サブプロセス、通信、削除、展開(`extractall`)を、ソースに含まない(テストが検査) |

## 6. 確認できていないこと

自宅の Mac では、手で組み立てた最小の docx / xlsx / pptx と、最小の PDF でテストしている。**本物の Word / Excel / PowerPoint が作った複雑なファイルでは、まだ試していない。** 実機の Windows で、PDF の取り出し(日本語の PDF を含む)も試していない。macOS の `textutil` で作った docx(スタイルも表も含まない)は、変換できた。

会社で確認する項目は [company-checklist.md](company-checklist.md) の 10 に書いた。特に次の点。

- 実際の文書で、見出し・表・箇条書きが期待どおりに出るか。Word で書式を直接指定しただけの見出し(スタイルを使っていない)は、見出しにならず、普通の段落になる。
- Excel で、日付が日付として出るか(書式の判定)。数式の結果が空欄にならないか。
- 日本語の PDF で、文字化けや順序の崩れがないか。
- 大きなファイル(数十 MB、数百ページ)で、時間とメモリが許容範囲か。

## 7. 形式を足すとき

`scripts/convert_core.py` の `CONVERTERS` に、変換する関数を足す。関数は `Result`(Markdown、種類、単位、注意)を返す。足したら、`tests/test_convert.py` に、最小のファイルを組み立てるテストを書く(外部のライブラリで作ったファイルに頼らない)。ファイルの書き込み・削除・実行・通信を足してはいけない(テストが検査している)。
